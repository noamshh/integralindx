The Theory Behind IntegralIndx

Understanding E-Graphs, E-Gen embeddings, and the architecture powering mathematical expression similarity search

Why I Built This

Written by Noam Shalev • 2025

In my mathematics research† I spend a lot of time searching for integrals online, mainly on Google and on Math StackExchange. It is often very frustrating because this kind of textual search works well only on very simple integrals, and even then I might miss useful results due to syntactic differences between my query and the seeked results. This happens because mathematical expressions can be written in many different ways due to several reasons, including: basic mathematical rules (commutativity, power rules, etc.), naming conventions (e^x vs. exp(x), arcsin vs sin^{-1}), or even personal taste in TeX formatting (arbitrary choice of the variable of integration, parameter names, and TeX commands).

For years, I had this idea in the back of my mind: build a proper, searchable integral database. I wanted a search engine that actually 'understands' mathematical expressions, providing an easy way to find other semantically similar integrals, something which simple bag-of-words approaches just can't do.

Only now, when I finally found some free time, and after delving deeper into machine learning theory at university, I realized how ridiculously complex this problem actually is. The key thing needed for such a search engine are good embeddings of mathematical expressions, ones that capture the actual semantic meaning of the symbols involved. So I started reading some literature. I found MathBERT (Peng et al., 2021), which showed impressive results on mathematical reasoning tasks. The thing is, it's fundamentally a language model. It's trained on mathematical text with surrounding natural language, learning to predict masked tokens based on textual context. Even though it works not too bad, I wanted something that understands pure mathematical equivalence without any surrounding text.

Then I found SemEmb (Gangwar & Kani, 2023), which creates embeddings over symbolic expressions directly. This seemed like exactly what I was looking for! It had decent results and was heading in the right direction. But then I stumbled upon the recent E-Gen (Zheng et al., 2025) paper, and I was genuinely thrilled. E-Gen took everything SemEmb was doing and pushed it much further. The greatest obstacle thus far was the very limited amount of meaningful training data available. The authors of E-Gen proposed a beautiful solution for this problem (using e-graphs), and showed how to generate massive synthetic datasets of equivalent expressions starting with only a small initial set of clean mathematical expressions. I immediately knew that i must try it out.

This demo is my attempt at putting my idea into practice, and build a search engine that actually understands mathematical expressions.

E-Graphs & E-Gen Overview

How Do We Get Good Embeddings of Mathematical Expressions?

The key insight is that embeddings need to capture semantic equivalence, not just syntactic similarity. If two expressions are mathematically identical, like sin²(x) + cos²(x) and 1, their embeddings should be close together in vector space. But how do you teach a neural network what "mathematically equivalent" means? The answer is to train it on pairs (or clusters) of equivalent expressions. By showing the model many (!) examples of expressions that mean the same thing but look different, it learns to recognize the underlying mathematical structure rather than just memorizing symbol patterns. As I mentioned, the main challenge is in the creation of a large enough corpus of such equivalence clusters, so that a model can actually read some signal off of the data.

SemEmb took this approach by generating equivalent expression pairs using SymPy's simplification functions. The problem is that SymPy is designed to find the most simplified form directly, without generating intermediate steps. This meant SemEmb was limited to cluster sizes of just 2 (pairs of expressions), missing out on the rich diversity of equivalent expressions that exist between the original and simplified forms.

E-Gen's Innovation: E-Graphs

E-Gen solves this limitation using e-graphs (equality graphs), a data structure originally invented in the 1980s by Nelson & Oppen for automated theorem proving. The idea of equality saturation (applying all possible equalities within an e-graph until saturation) was later leveraged for program optimization by Tate et al. (2009), and more recently, Willsey et al. (2021) developed the egg library, which made equality saturation fast and practical (via new techniques like efficient rebuilding and e-class analyses). Instead of producing just a pair of expressions, equality saturation starts with a seed expression and systematically applies mathematical rewrite rules to explore the entire space of equivalent forms. The e-graph compactly represents all these equivalences in "e-classes", where each e-class contains expressions that are mathematically identical (see this blogpost for a really nice introduction to e-graphs).

This enables E-Gen to generate dozens or even hundreds of equivalent forms per seed expression, creating rich training datasets where each expression becomes a large cluster of mathematically equivalent variants. A transformer trained on these massive clusters using contrastive learning (pulling equivalent expressions together, pushing unrelated ones apart) learns to capture deep semantic relationships rather than surface-level syntactic patterns.

Figure 1: Overview of E-Gen and the cluster-based training framework. Equivalent expressions of each initial expression are generated using an e-graph-based approach, forming clusters of equivalent expressions. The original E-Gen paper implemented both a seq2seq model (trained on equivalent expression pairs) and a contrastive learning model (trained on triplets). For IntegralIndx, I chose to focus on the contrastive learning approach because it's more efficient for similarity search tasks, learning embeddings directly without requiring a decoder.
Source: Zheng et al. (2025), "E-Gen: Leveraging E-Graphs to Improve Continuous Representations of Symbolic Expressions." Figure 2.

The key insight is that expressions like x² + 2x + 1 and (x + 1)² are mathematically identical, and their embeddings should reflect this equivalence. E-graphs provide the machinery to systematically generate and exploit these equivalences during training, going far beyond what simple rewrite rules can achieve.

Data Collection & Processing Pipeline

Of course, good embeddings mean little without actual data to embed. I turned to Math StackExchange for the data, knowing that it contains thousands of high-quality integrals from real problems, that people asked about and cared to solve. Better yet, each integral can be linked to its source discussion, which often includes the context in which this integral arises, possible closed-forms, and a variety of solution attempts.

When I started this project, I thought the data part would be straightforward. Scrape the integrals from MSE, throw them in a database, and move on to the interesting ML work. Naive me.

Data processing is easily the hardest part of this entire project. Real-world LaTeX from MSE is messy, inconsistent, and filled with edge cases I never imagined. People write integrals in dozens of different ways, use custom macros, nest them in complex equation environments, and mix them with narrative text. I needed to convert all of this dirty, real-world LaTeX into a clean, normalized form that could be reliably parsed.

Why can't we just use the LaTex as is?

LaTeX is designed for typesetting, not semantic analysis. The expression x² can be written as x^2, x^{2}, {x}^{ 2 }, and many other variations which result in the same visuals. These different strings would be treated as unrelated epxressions if we were to tokenize LaTeX directly. SymPy provides semantic parsing: a canonical tree representation that stays the same regardless of how the expression was typeset. This semantic representation is useful here for two reasons: first, it gives an easy way to convert the expression to prefix notation (pow x 2), which is a good format to apply tokenization to, and second, it allows us to use SymPy's simplification functions to deduplicate integrals by their canonical integrand.

But getting to that point required building custom parsing logic to clean the raw MSE data. After applying a plethora of hand-tailored normalization and filtering rules (which I'll describe below), we still need to convert the cleaned LaTeX into SymPy format. While there are some good LaTeX-to-SymPy parsers out there, nothing exactly fit my requirements. I ended up forking the latex2sympy2_extended package (which is itself a fork of previous latex2sympy versions) and adding custom parsing capabilities for some special functions. Even then, I had to be pretty restrictive: blacklisting certain LaTeX commands that caused parsing issues, setting timeouts on the parser (20 seconds per expression), and rejecting anything that looked remotely ambiguous. I'm sure I lost thousands of potentially valid integrals in the process, but reliability was more important than coverage.

What started as "just scrape and parse" became a multi-stage pipeline with normalization, validation, deduplication, and variable canonicalization. Let me walk you through it.

Pipeline Overview

From 206k raw MSE expressions to 23,638 integrals in 12,337 unique groups:

  1. MSE Scraping: Query Math StackExchange API with 20 integral-related tags
    • Tags: closed-form, integration, definite-integrals, special-functions, polylogarithm, etc.
    • 80 pages per tag, 100 questions per page, sorted by votes
    • Result: 206,328 raw LaTeX expressions from questions and answers
  2. LaTeX Normalization: Clean and structure the raw LaTeX
    • Parse LaTeX environments (align, equation, etc.)
    • Extract relation chains (A = B = C --> [A, B, C]) to capture equivalent forms
    • Separate parametric conditions (e.g., "for x > 0")
  3. Integral Extraction & Validation: Parse and validate integral expressions
    • Advanced parsing for definite and indefinite integrals
    • SymPy validation to ensure mathematical correctness
    • Quality filtering and deduplication
    • Result: 26,730 validated integrals
  4. Variable Normalization & Grouping: Canonicalize for ML training
    • Standardize integration variables: t, y, z --> x
    • Normalize parameters to alphabetical ordering: a, b, c (max 3 parameters)
    • Group by unique integrand hash after simplification
    • Result: 12,337 unique integrand groups from 23,638 instances

    5. I do hope to find the time in the future to scale up this database, and create similar databases for sums, products, and special functions.

Model Architecture & Training

Transformer Architecture

IntegralIndx uses an encoder-only transformer architecture for generating mathematical expression embeddings. The model processes tokenized expressions in prefix notation and produces vector representations via mean pooling. Unlike seq2seq, this architecture directly optimizes for embedding quality through contrastive learning, making it ideal for similarity search tasks.

Contrastive Learning

The model is trained using contrastive learning with the InfoNCE loss (temperature=0.1). This is a self-supervised approach: rather than requiring manual labels, the model learns from equivalence clusters generated automatically via e-graph rewrite rules. Given a query expression and its positive equivalent, the loss maximizes their cosine similarity while minimizing similarity to negative samples (randomly sampled from other clusters). This forces the encoder to learn representations where mathematically equivalent expressions cluster together in the 512-dimensional embedding space.

Training Data Generation

Training data was generated through a two-stage pipeline:

  1. Seed Selection: 1,793 seed expressions were frozen for training:
    • 337 hand-crafted synthetic seeds covering common patterns (polynomials, trig identities, logarithms, etc.)
    • 1,456 expressions extracted from the IntegralIndx database with max token length = 8
    • Token limit ensures E-Gen can generate rich, diverse equivalents without timing out
  2. E-Gen Equivalence Generation: Apply E-Gen to each seed. Of the 1,793 seeds, 1,243 seeds successfully generated equivalents (69.3% success rate), producing an average of 154 equivalents per seed (median: 74). This resulted in 191,394 total equivalent expressions across all clusters. The variability in cluster sizes reflects the mathematical complexity of different expressions: simple expressions often yield larger clusters, while complex expressions may have fewer equivalent forms within the token limit.
  3. TSV Construction: Split seeds 80/10/10 (train/val/test). For each seed, generate all pairwise combinations (query, positive) and sample 3 negatives from other clusters within the same split (clusters with more than 200 equivalents are restricted to 70 positives per query via random sampling to prevent over-representation). The dataset is stored in TSV (tab-separated values) format for efficient loading.
    • Train: 12.68M lines (994 seeds)
    • Validation: 1.59M lines (124 seeds)
    • Test: 1.46M lines (125 seeds)
    • Total: 15.73M training quintuples (query, positive, neg1, neg2, neg3)
Training Procedure

The model was trained for 4 epochs over 49 hours on a rented L40S GPU via Vast.ai (totaling $35). The production model uses checkpoint 175,000 (3.5 epochs, 43 hours), as the final checkpoint was accidentally deleted (sigh). Training used the AdamW optimizer with cosine annealing and a 1-epoch warmup schedule. The warmup phase linearly increases the learning rate from 1e-5 to 1e-4, after which the learning rate decays via cosine annealing to a minimum of 1e-6.

FAISS Similarity Search

Once the transformer model has generated 512-dimensional embeddings for all integrand groups in the database, the next challenge is efficient similarity search: given a query embedding, how do we quickly find the most similar integrands among thousands of candidates? This is where FAISS (Facebook AI Similarity Search) comes in. FAISS is a library developed by Facebook AI Research for efficient similarity search and clustering of dense vectors. It's optimized for large-scale vector search operations and is widely used in recommendation systems, image retrieval, and natural language processing. FAISS provides both exact and approximate nearest neighbor search algorithms, with support for CPU and GPU acceleration.

IntegralIndx uses IndexFlatIP (Flat Inner Product), which performs exact search using dot product similarity. Note that mathematically, via L2-normalization, dot product similarity is the same as cosine similarity. The flat index guarantees exact nearest neighbors (no false negatives), which naturally requires more compute (flat index requires O(n) comparisons), but with our n=12k database this is less than 10ms on a modern CPU. For larger datasets, approximate indexes like IVFFlat or HNSW would be faster.

Search Pipeline

When you submit a query integrand, the system performs the following steps:

  1. Variable normalization: query --> normalize to x, a, b, c (same as training)
  2. SymPy conversion: normalized query --> SymPy (validated syntax and allowed functions)
  3. Prefix notation: SymPy --> space-separated prefix tokens
  4. Tokenization: prefix tokens --> token IDs using vocabulary
  5. Embedding: token IDs --> 512D embedding vector (via the trained encoder)
  6. L2 normalization: embedding --> unit vector (for cosine similarity)
  7. FAISS search: find top-k nearest neighbors
  8. Result formatting: return integrand groups with similarity scores

Closing Thoughts

So that's IntegralIndx: from an idea I had years ago to a working semantic search engine built on e-graphs and contrastive learning. It's far from perfect: the database is still small, the normalization pipeline could be more efficient, training could be longer, and I'm certain there are parsing errors lurking in edge cases I haven't encountered yet. But it does what I wanted: you can type in an integral, and it actually understands what you're looking for, not just what characters you typed. Whether you're a student stuck on a homework problem or a researcher hunting for closed forms, I hope this makes finding relevant integrals a little less frustrating than it was for me.
